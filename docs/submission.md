## Быстрые команды

Выполнять из корня `Tumo-CQA`, Node.js >=24, с установленными зависимостями. **`path`, `UUID`, `EXACTNAME` и `previouslysavedAPIversion` ниже — только плейсхолдеры**, не готовые значения и не название команды. Замените их путём полного исходного набора, UUID версии из API, подтверждённым точным названием и путём сохранённого объекта версии соответственно. Пути и названия с пробелами заключайте в кавычки.

Обработка с последующим экспортом, два альтернативных способа задать версию:

```sh
npm run results:prepare -- --split dev --dataset path --version UUID --team EXACTNAME
npm run results:prepare -- --split dev --dataset path --version-file previouslysavedAPIversion --team EXACTNAME
```

Укажите ровно один из `--version` и `--version-file`. Вместо `--team` можно задать `TEAM_NAME` в окружении, в том числе через локальный `.env`; явно переданный `--team` имеет приоритет. Для экспорта название обязательно. Валидатор проверяет непустую строку, **но не может подтвердить её правильность за команду**.

Пока название не согласовано, можно готовить только закрытый журнал, например порциями по пять диалогов:

```sh
npm run results:prepare -- --split dev --dataset path --version-file previouslysavedAPIversion --prepare-only --max-new 5
```

Повтор той же команды продолжает необработанные ID. Уберите `--max-new`, чтобы обработать все оставшиеся. `--prepare-only` не требует команды, но делает реальные вызовы модели; официальный output не записывает даже при полном журнале.

После завершения журнала и подтверждения названия — экспорт без повторного обращения к модели, затем отдельная проверка файла:

```sh
npm run results:prepare -- --split dev --dataset path --version-file previouslysavedAPIversion --team EXACTNAME --export-only
npm run results:prepare -- --split dev --dataset path --version-file previouslysavedAPIversion --validate-only
```

**В показанном варианте с `--version-file` экспорт и валидация не делают API-вызовов вообще.** Если вместо него использовать `--version UUID`, CLI всё ещё обращается к локальному API за версией, но не к провайдеру модели. `--export-only` требует существующий полный журнал и совместимые текущие модель/настройки/исходники, хотя ключ провайдера ему не нужен. Полный журнал может содержать `status="error"`: это завершённые попытки, не успешные оценки. `--validate-only` не требует ключа или `--team`, проверяет уже записанный `team_name` и не меняет output либо журнал.

Повтор ошибок — только по явному решению, с возможным дополнительным расходом API:

```sh
npm run results:prepare -- --split dev --dataset path --version-file previouslysavedAPIversion --prepare-only --retry-errors --max-new 5
```

`--retry-errors` выбирает ошибочные **и ещё не обработанные** диалоги, не повторяет успешные. По умолчанию ошибки сохраняются без повтора. Внутри одной оценки разрешён один repair невалидного ответа; автоматических повторов сети/HTTP/тайм-аута нет. `--max-new` ограничивает число оцениваемых диалогов за запуск, а не число HTTP-запросов: repair может потребовать второй запрос.

Режимы `--prepare-only`, `--export-only`, `--validate-only` взаимоисключающие; `--export-only` нельзя совмещать с `--retry-errors`.

## Данные и реальная версия чек-листа

- `--dataset` обязателен также для экспорта и валидации. Принимается массив записей, `{records}` или исходный ответ организаторов с `isSuccess=true` и `data.records`. Предварительный импорт в SQLite не требуется: CLI работает с локальным набором и не создаёт backend jobs/evaluations.
- DEV — **ровно 65 диалогов: 60 чатов и 5 звонков**, языки исходного набора — 35 RU, 15 KZ, 15 EN. CLI проверяет размер, каналы, уникальность исходных ID, формат записей и, при наличии, метаданные размера/группы. Полный ответ нужен без отбора только удачных диалогов.
- `conversation_id` всегда берётся из исходных данных организаторов. Внутренний UUID диалога из базы не является заменой. Экспорт сохраняет исходный порядок и ровно одну строку на каждый исходный ID, включая ошибки.

Для выбора версии используйте существующий сервер:

```sh
curl --fail http://127.0.0.1:3000/api/checklists
```

Выберите UUID из `latest_version.id` либо ранее сохранённой версии. С `--version` CLI получает `GET /api/checklists` и `GET /api/checklist-versions/:id`, проверяет принадлежность версии этому API; для другого сервера задайте `--api-base`. `v1`, `latest`, выдуманный UUID и UUID из другой базы не подходят.

`--version-file` читает **полный неизменённый объект версии, ранее полученный через API**, включая метаданные, а не строку UUID или вручную собранный `defaultConfig`. После сохранения snapshot работа может продолжаться без сервера. Нельзя заменять его свежим «эквивалентным» объектом посреди прогона.

Если отдельно подготовлен `data/ai-results/dev-checklist-version.json`, это локальный snapshot ответа уже существующего изолированного API с отдельной временной БД, а не встроенный чек-лист и не default-путь CLI. Наличие такого файла эта инструкция не подтверждает; передавайте его явно через `--version-file`. После закрытия временной БД её UUID **нельзя считать существующим на рабочем сервере** и передавать там как `--version`: используйте сохранённый объект для этого прогона либо получите настоящую версию рабочего API для отдельного прогона.

### Исходная рубрика и границы оценки

Официальный экспорт строго требует исходные `c1`–`c8`: тексты, секции, веса, типы, шкалы и правила N/A должны совпадать с исходной нормализованной конфигурацией. Изменённая через UI рубрика пригодна для динамической оценки, **но этот экспорт её отклоняет**, чтобы не выдать новый критерий под прежним официальным кодом.

Для `contact` сохранено строгое boolean-правило PDF: оператор поздоровался на языке клиента **и представился в первом ответе**. N/A не разрешён. Неоднозначность между PDF и Q&A этим экспортом не разрешается: иное толкование требует подтверждения организаторов, а не молчаливого ослабления рубрики.

Звонки по умолчанию оцениваются **только по выданному транскрипту**. Аудио не скачивается и модели не передаётся; выводы о дикции и интонации не заявляются. Нумерация доказательств идёт с 1 по всему исходному `transcript`, включая bot/system; оценивается работа operator, остальные роли служат контекстом.

## Журнал, возобновление и ограничения

| Параметр / путь | Поведение |
| --- | --- |
| `--journal` | По умолчанию `data/ai-results/dev-preparation.json` для DEV; для PROD — `data/ai-results/prod-preparation.json`. Закрытый checkpoint после каждого завершённого диалога. |
| `--output` | По умолчанию `results/dev/results.json` или `results/prod/results.json`. Записывается только при полном покрытии набора вне `--prepare-only`. |
| `--max-new N` | Положительное число диалогов для очередной порции; без параметра — все оставшиеся кандидаты. |
| `--concurrency N` | По умолчанию **1**, допустимо **1–3**. Это параллелизм только CLI, не изменение последовательной backend-очереди и не лимит аккаунта провайдера. |
| `--delay-ms N` | По умолчанию 1000 мс перед следующим диалогом в каждом worker, допустимо 0–60000. Не глобальный rate limiter. |

CLI вызывает AI-модуль напрямую, поэтому `AI_ENABLED=true` для него не требуется. Журнал не является кэшем SQLite и не переносит результаты в API апелляций. Не задавайте output/journal поверх dataset или snapshot версии.

Возобновление допускается **только при совпадении контракта**: хеша нормализованных диалогов с их порядком и используемыми полями, полного объекта версии **включая метаданные**, модели, `prompt_version`, хешей учитываемых исходников/промптов/схем и параметров `AI_BASE_URL`, `AI_STRUCTURED_OUTPUT`, `AI_MAX_TOKENS`, `AI_PROVIDER`, `AI_REASONING_EFFORT`. Проверяется также сам сохранённый объект версии. Смена UUID/метаданных версии, данных, модели, промпта, учитываемого кода или этих параметров приводит к отказу, а не смешиванию результатов.

**Не обещайте повторное использование журнала с другими входами**, даже если рубрика выглядит одинаково. Для нового контракта нужен отдельный `--journal` и, чтобы не спутать артефакты, отдельный `--output`. Повреждённый журнал автоматически не затирается. Для `--export-only` сохраняйте настройки исходного прогона: отсутствие вызовов модели не отменяет проверку fingerprint.

Эксклюзивный файл `<journal>.lock` предотвращает одновременную подготовку с одним журналом. При штатном выходе он снимается; после аварийного kill может остаться. **Автоматического снятия stale lock нет.** Сначала проверьте список процессов и убедитесь, что процесс-владелец и его активная работа действительно завершены; только после этого можно вручную удалить оставшийся lock. Не удаляйте его по одному возрасту файла и не запускайте второй процесс, пока первый работает.

## Официальный JSON 1.0

Полная машиночитаемая спецификация — [submission-v1.json](../server/schemas/submission-v1.json); большой пример JSON здесь не дублируется. Лишние поля запрещены, приведения типов нет.

Корень содержит ровно `schema_version: "1.0"`, непустой `team_name`, `model: {mode, name}` и массив `results`. Допустимые `model.mode`: `local`, `external_api`, `hybrid`; данный CLI пишет `external_api`, а `model.name` берёт из реально настроенного AI-модуля. Для выбранного split нужны ровно 65 или 10 уникальных исходных ID.

Успешная строка: `conversation_id`, `status: "ok"`, восемь `criteria` и `score: {final_score, critical_flag}`. У критерия ровно `criterion_id`, `value`, непустой `rationale`, непустой `evidence_turns`.

| Официальный `criterion_id` | Внутренний ID | Допустимый `value` | Вес |
| --- | --- | --- | --- |
| `contact` | `c1` | `true`, `false` | 10 |
| `discovery` | `c2` | `true`, `false`, `null` | 15 |
| `identification` | `c3` | `true`, `false`, `null` | 20 |
| `consultation` | `c4` | `0`, `5`, `10`, `15`, `20`, `null` | 20 |
| `empathy` | `c5` | `true`, `false` | 15 |
| `dialogue` | `c6` | `0`, `4`, `7`, `10` | 15 |
| `closure` | `c7` | `true`, `false`, `null` | 5 |
| `critical` | `c8` | `true`, `false` | 0, отдельный флаг |

Это JSON boolean/number/null, не строки `"yes"`, `"false"`, `"N/A"` и не взаимозаменяемые `false`, `0`, `null`. Шкальные значения — исходные ступени, **не взвешенные баллы**. Все восемь кодов должны присутствовать ровно один раз.

- `null` означает только разрешённое N/A: для `discovery` — данных хватало с начала; `identification` — запрос не требовал проверки личности; `consultation` — чат закончился до формулировки запроса; `closure` — оборвался до возможности завершить. Пропущенное необходимое действие — не N/A.
- `critical=true` означает обнаруженную грубую ошибку, а не успешное выполнение. `score.critical_flag` обязан точно совпадать с ним. Флаг не обнуляет итог.
- `score.final_score` — число 0–100, пересчитанное существующим `calculateScore()` из `score.js`. Формула не менялась: `100 × Σ(вес × доля выполнения) / Σ(применимые веса)`, где boolean даёт 1/0, шкала — балл/максимум. N/A исключается из обеих сумм, итог округляется до двух знаков; `critical` с нулевым весом не участвует. В исходной рубрике остаются применимые весовые критерии, поэтому у `ok` итог не `null`.

### Доказательства и объяснения

`rationale` сохраняет исходное объяснение. Для N/A в него дописывается `Причина N/A: …`, при наличии диапазона — `Проверены реплики from–to.`. `evidence_turns` — отсортированное объединение **всех исходных evidence-индексов и каждой реплики всего включительного `checked_range`**, без повторов; это не только границы диапазона. Все индексы должны существовать в соответствующем исходном транскрипте.

При подготовке строгий AI-контракт требует `checked_range` для `no`, частичной шкалы или пустого исходного evidence. Так проверенный участок не теряется при переходе в официальный формат, где отдельного поля `checked_range` нет. Проверка индексов и наличия текста не доказывает фактическую правильность вывода: диапазоны, N/A и обоснования нужно просмотреть человеку.

### Ошибки — не нулевые оценки

Неуспешная обработка сохраняется отдельной строкой с тем же исходным `conversation_id`, `status: "error"`, `criteria: []`, `score: null` и непустой безопасной строкой `error`. Успешные поля с ошибкой не смешиваются. Нельзя подставлять нулевой итог, восемь `false` или N/A вместо сбоя модели.

В `error` нельзя публиковать сырой ответ провайдера, ключи, URL, JSON или stack trace; CLI использует безопасные категории причин. Такие строки сохраняют полное покрытие набора и допустимы структурно, но не означают выполненную качественную оценку.

## Валидация и коды выхода

`--validate-only` проверяет точную схему/типы, полное множество исходных ID без дублей, восемь кодов у каждой `ok`-строки, допустимые значения/N/A, индексы evidence по исходному транскрипту, безопасную форму ошибок, соответствие `critical_flag` и повторный серверный расчёт `final_score`. Самой JSON Schema недостаточно для проверки покрытия ID и пересчёта: используйте CLI с исходным dataset и той же версией.

| Ситуация | Код выхода | Официальный output |
| --- | --- | --- |
| Полный обычный запуск или `--export-only`, все строки `ok` | `0` | Записан и проверен |
| Полный экспорт, есть строки `error` | `1` | **Записан и валиден**, ошибки не скрыты |
| Журнал неполный, режим не `--prepare-only` | `2` | Не создаётся и не обновляется |
| `--prepare-only` завершил свою порцию, в том числе неполную или с ошибками | `0` | Не записывается; смотрите `pending`/`errors` в сводке |
| `--validate-only`, структура и проверки проходят, даже при строках `error` | `0` | Существующий файл проверен, не изменён |
| Неверные аргументы/данные/версия, lock, несовместимый или повреждённый журнал, сбой записи/валидации | `1` | Успешный новый экспорт не подтверждён; изучите причину |

При неполном прогоне прежний output **не удаляется**. Одно наличие `results.json` не доказывает, что он от текущего запуска: проверяйте код выхода, сводку и валидацию по нужным входам.

**PASS в `--validate-only` — структурная и вычислительная корректность, не семантическое качество и не отсутствие строк `error`.** Число успешных тестов кода также не является качеством реальной модели. Итоговый отчёт полного DEV-прогона составляется отдельно после завершения: фактические ok/error/pending, попытки/repair, время, доступные данные стоимости и результаты ручного разбора, без переноса цифр предварительных выборок.

## Приватность, публикация и PROD

- Ключ провайдера храните **только в локальном `.env`**, не в командах, Markdown, frontend или Git. `npm run results:prepare` уже запускает Node с `--env-file-if-exists=.env`; не печатайте ключ для проверки. Для реальной оценки нужен `AI_API_KEY`; экспорт/валидация с сохранённой версией обходятся без него.
- `data/ai-results/dev-preparation.json`, возможный snapshot версии и диагностика в `data/` — закрытые локальные артефакты, весь `data/` исключён из Git, как и `.env`. Файлы журналов/результатов записываются с правами `0600`, новые каталоги — `0700`. Собственные пути вне `data/` требуют отдельного контроля доступа и исключений Git.
- `results/dev/results.json` — **предназначенный для публичной сдачи** артефакт, не исключённый текущим `.gitignore`. В нём нет полей полного `transcript`, `audio_url` или сырого HTTP-ответа, но **`rationale` может содержать цитаты и персональные данные**. Права файла и санитарная обработка ошибок не обеспечивают обезличивание. До любой публикации человек должен проверить разрешение на раскрытие, тексты и точное `team_name`.
- Реальные вызовы передают текст диалогов и конфигурацию внешнему провайдеру; согласуйте обработку, хранение и обезличивание. Не считайте вызовы бесплатными или стоимость измеренной по названию модели: нужны актуальные условия и фактический `usage`, включая repair и явные повторы. Пока данных полного прогона нет, стоимость и длительность не заявляются.
