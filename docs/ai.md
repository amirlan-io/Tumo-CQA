# Модуль оценки Tumo-CQA — версии промпта v1/v2/v3

## Статус и границы

Реализован `evaluateDialogue()`, строгая проверка JSON, диагностические файлы, одиночный CLI и сравнение моделей. Маршруты, база, `score.js`, очередь и кэш не изменены. Используется существующий контракт `server/index.js` / `server/jobs.js`.

**Ключ и реальные вызовы проверены:** Crouton v1 вернул валидные итоговые ответы для 9/9 DEV-диалогов; в двух случаях понадобился разрешённый repair. Совпадение с draft — **56/72 (77,8%)**, не точность на утверждённом эталоне. Реальный пример `p1-kz-013` с 8/8 совпадениями сохранён в `data/ai-results/single.json`. Качество ещё требует доработки и человеческого согласования: подробности в [ai-validation.md](ai-validation.md).

Доступен экспериментальный промпт `v2` и парный CLI `ai:compare-prompts`. На новом опыте из 18 диалогов он улучшил совпадение с draft, но не уменьшил неподтверждённые фактические утверждения и допустил регрессию по исключённому SLA. **По умолчанию остаётся v1**, полный DEV-файл не перезаписан. Методика, ограничения и результаты: [prompt-v2-experiment.md](prompt-v2-experiment.md).

Проверены шесть гипотез причин ошибок: 40 реальных оценок API, отдельный source-аудит и слепая повторная разметка. Обнаружена нестабильность 4/24 решений при идентичных запросах; разбиение критериев и quote-first не показали надёжного устранения содержательных ошибок. Подробные числа и ограничения: [hypotheses-results.md](hypotheses-results.md). Рабочий промпт и официальный DEV-файл по итогам этого пилота не заменялись.

После обновления backend до `a7a8b3c` добавлен opt-in кандидат `v3`: явные исключения, приоритет N/A, проверка отрицательных утверждений по диапазону и динамическое число критериев. На новом общем успешном срезе он превзошёл v1 (40/48 против 38/48), но не v2 (51/56 против 52/56); знаменатели этих пар относятся к разным подмножествам. **V3 не прошёл quality gate и не включён по умолчанию.** Подробности, сбои и source-аудит: [prompt-v3-experiment.md](prompt-v3-experiment.md).

## Установка и настройки

Требуется Node.js >=24. Команды выполнять из каталога `Tumo-CQA`:

```sh
npm ci
cp .env.example .env
```

Укажите `AI_API_KEY` только в `.env`. Не отправляйте ключ в чат, frontend, аргументы CLI или Git. `.env` и `data/` исключены из Git. Node загружает файл через `--env-file-if-exists=.env`, дополнительный `dotenv` не нужен.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `AI_API_KEY` | нет | Ключ выбранного API, обязателен для оценки |
| `AI_BASE_URL` | `https://openrouter.ai/api/v1` | HTTPS-база OpenAI-compatible Chat Completions, без `/chat/completions` и query/credentials |
| `AI_MODEL` | `stealth/crouton-alpha` | Явный ID модели, без автоматической подмены |
| `AI_PROMPT_VERSION` | `v1` | Явный выбор `v1`/экспериментальных `v2`/`v3`; для сервера нужен перезапуск. Кандидаты не рекомендованы как default по текущим проверкам |
| `AI_STRUCTURED_OUTPUT` | `json_schema` | Строгая схема; `json_object` — только для API без поддержки схемы, локальная проверка остаётся |
| `AI_TIMEOUT_MS` | `55000` | Общий бюджет запросов, исправления и ожидания диагностики; не больше 55000 мс |
| `AI_REQUEST_TIMEOUT_MS` | `35000` | Лимит одного HTTP-вызова, дополнительно ограниченный оставшимся общим бюджетом |
| `AI_MAX_TOKENS` | `4096` | Бюджет ответа; у reasoning-моделей в него может входить reasoning |
| `AI_DIAGNOSTIC_DIR` | `data/ai-diagnostics` | Закрытый каталог с исходными ответами провайдера |
| `AI_PROVIDER` | не задан | Необязательный pin провайдера OpenRouter; для сравнения разных моделей оставьте незаданным |
| `AI_REASONING_EFFORT` | `minimal` для Crouton, иначе не задан | Необязательная model-specific настройка OpenRouter, не часть промпта |
| `AI_ENABLED` | `false` | Существующее серверное подключение. `true` подключает модуль к готовым jobs после перезапуска |

Сначала можно оставить `AI_ENABLED=false`: CLI напрямую вызывает функцию, не создавая оценок/заданий в базе. Сервер нужен для получения **реальной сохранённой версии чек-листа**:

```sh
npm start
```

## Первая контрольная точка: один реальный диалог

В другом терминале получите список чек-листов:

```sh
curl --fail http://127.0.0.1:3000/api/checklists
```

Выберите нужный `latest_version.id` либо ID более ранней версии. CLI требует явный UUID и запрашивает оба endpoint: `GET /api/checklists`, затем `GET /api/checklist-versions/:id`. Он проверяет принадлежность версии и не переключается на latest молча.

Для предоставленного `invoke.json`:

```sh
npm run ai:evaluate -- \
  --version UUID_ВЫБРАННОЙ_ВЕРСИИ \
  --conversation p1-ru-001 \
  --dataset "/home/angel/Загрузки/Telegram Desktop/invoke.json"
```

Замените `UUID_ВЫБРАННОЙ_ВЕРСИИ` реальным ID из API. Переписки не нужно заранее импортировать: локальный dataset читается без изменения базы. Без `--dataset` CLI получает выбранный диалог через `GET /api/conversations` и `GET /api/conversations/:id`.

**Артефакт реального успешного вызова:** `data/ai-results/single.json`, только `{model,prompt_version,results}` с восемью ответами, без времени/итога. Время выводится отдельно. Файл создаётся только после успешной проверки реального ответа. Сейчас в нём извлечённый без правок результат `p1-kz-013` из реального предварительного benchmark (8231 мс, одна попытка), не синтетический пример. При ошибке старый файл не удаляется: проверяйте код завершения команды, а не одно лишь наличие результата предыдущего запуска. Для нового измерения можно задать отдельный `--output`.

## Контракт функции

```js
import { evaluateDialogue, model, prompt_version } from './server/services/ai.js';

const output = await evaluateDialogue(conversation, checklistVersion, { signal });
// { model, prompt_version: 'v1', results: [ /* по одному на критерий версии */ ] }
```

`conversation` — объект с `language`, `channel`, `transcript` и необязательным ID. Формат реплик — `timestamp`, `speaker`, `text`. `checklistVersion` — **полный объект выбранной версии из API**, не строка `v1` и не встроенный чек-лист. Сервер уже передаёт оба объекта из неизменяемого snapshot задания; модуль не делает HTTP-запрос к собственному серверу. `signal` необязателен, но учитывается для отмены fetch и ожидания записи диагностики.

В модель передаются название/ID/номер версии, округление и все настройки каждого критерия: `criterion_id`, `text`, `section`, `weight`, `answer_type`, `scale` с описаниями, `allow_na`, `na_rule`, `is_gross_error`. Никакого lookup по `c1…c8`: замена текста, ID, типа, шкалы или N/A через UI применяется без изменения модуля. `defaultConfig` используется только существующим сервером при создании первого чек-листа и тестами, не evaluator.

Нумерация задаётся по порядку всего исходного массива, с 1, включая bot/system. Неиспользуемые поля, внутренние заметки и `audio_url` не передаются. Аудио не скачивается; для звонков оценивается только выданный транскрипт, без выводов о дикции/интонации.

Обновлённый upstream-контракт допускает 1–50 критериев. Текст v3 также использует динамическое N; исторические неизменённые v1/v2 описывают восьмикритериальную задачу, поэтому результаты их проверок относятся к официальной восьмёрке. Offline-тесты кандидата проверяют N=1,8,9 и произвольные ID/шкалы; это проверка контракта, не доказательство семантического качества на произвольном новом чек-листе.

### Проверки ответа

- Корень — только `results`; metadata добавляет код из закреплённой конфигурации, не модель.
- Ровно столько объектов, сколько критериев выбранной версии, и точное множество её уникальных ID. Порядок на выходе соответствует настройкам. Для официального чек-листа это восемь.
- Только `yes/no/scale/na`; обычный boolean: `yes=1`, `no=0`; грубая ошибка: `yes/no` и `raw_score=null`.
- Для scale разрешены только заданные ступени, для N/A — разрешение критерия, `null` и непустая причина.
- Все обязательные поля присутствуют, лишние поля/общие итоги запрещены; вне N/A причина строго `null`.
- Evidence — уникальные целые индексы существующих реплик. Диапазон включительный, валидные границы.
- Для каждого `no`, частичного шкального балла и пустого evidence требуется `checked_range`. Для пропуска действия это диапазон, где оно ожидалось.
- Объяснения/причины должны быть непустыми и содержать русский текст. Проверка наличия кириллицы не доказывает, что весь текст по-русски: это дополнительно проверяется при ручном аудите.

Промпт: [`server/prompts/evaluate-v1.txt`](../server/prompts/evaluate-v1.txt). Изолирует транскрипт как недоверенные данные, оценивает только operator, различает пропуск и неприменимость, запрещает выдумывать правила компании и цитаты. Защита промптом/схемой **не гарантирует фактическую верность evidence или устойчивость ко всем prompt injections**. Локально проверяется форма и ссылки, семантика требует разметки и ручного аудита.

При правке промпта, схемы или семантики обработки изменяйте `prompt_version` вместе с файлом/именем схемы: сервер учитывает версию в ключе кэша. Перезапускайте процесс после изменения модели/настроек; экспорты фиксируются при импорте.

## Сбои и диагностика

Один первоначальный запрос на все критерии. Если ответ синтаксически/структурно/семантически некорректен по локальному контракту, возможен **ровно один** новый вызов с исходным диалогом, ошибками валидатора и предыдущим ответом, помеченным как недоверенные данные. Оба вызова делят общий тайм-аут. Markdown не вырезается, баллы и реплики не «чинятся» эвристиками.

Сеть, HTTP-ошибки, отказ модели и timeout не запускают repair. При повторной ошибке функция отклоняет Promise без `results`. Код ошибки: `AI_CONFIG`, `AI_INPUT`, `AI_UNAVAILABLE`, `AI_REFUSED`, `AI_INVALID_RESPONSE`, `AI_TIMEOUT`, `AI_CANCELLED` либо `AI_DIAGNOSTICS`. `AI_TIMEOUT` имеет `timeout=true`, совместимый с jobs. Нет автоматической смены модели, транспорта с неявными retries или выдуманной запасной оценки.

Каждый полученный ответ сохраняется в отдельный JSON: HTTP-конверт, status, ошибки валидации, время, модель и ID попытки. Ключ редактируется даже при случайном echo. Заголовки и исходный запрос с перепиской не логируются. Файлы — `0600`, новые каталоги — `0700`, штатные результаты тоже приватны. Ответы/объяснения всё равно могут содержать данные клиента: ограничьте доступ и срок хранения, не публикуйте `data/`. Для собственного `AI_DIAGNOSTIC_DIR` вне `data/` настройте исключение из Git самостоятельно.

Если отмена/deadline наступили во время файловой записи, функция не ждёт диск: начатая запись может закончиться в фоне, её ошибка обработана. На аварийном диске гарантировать сохранение невозможно. Без успешной записи до deadline валидная оценка не возвращается.

## Выбор модели и приватность

Начальный **кандидат**, а не доказанный победитель: OpenRouter `stealth/crouton-alpha`. Endpoint заявляет поддержку `json_schema`, reasoning и `temperature`. Второй кандидат — `openai/gpt-4.1-mini` с теми же prompt/input/schema. Structured outputs не заменяют локальную проверку. Для OpenRouter включены `require_parameters=true`, `allow_fallbacks=false`; без поддерживаемых параметров запрос должен явно завершаться ошибкой, а не ослаблять контракт.

Crouton — анонимная preview-модель. По публичной странице провайдер может хранить запросы и ответы; обучение на них исключено в опубликованном описании, но это не равно отсутствию хранения. Перед отправкой рабочих переписок согласуйте передачу третьей стороне и обезличивание. В API уходят текст и конфигурация, но не ключи из других настроек или signed URL аудио. Не отправляйте записи только потому, что модель бесплатная.

На дату проверки публичного каталога, 2026-11-07: Crouton — $0 за вход/выход; GPT-4.1-mini — $0.40/$1.60 за 1 млн входных/выходных токенов. Это тарифы, **не измеренная стоимость диалога**. Реальную стоимость считайте по `usage` сохранённых HTTP-ответов, включая repair и reasoning, по тарифу провайдера на дату запуска.

Источники:
- https://openrouter.ai/stealth/crouton-alpha
- https://openrouter.ai/api/v1/models/stealth/crouton-alpha/endpoints
- https://openrouter.ai/api/v1/models/openai/gpt-4.1-mini/endpoints
- https://openrouter.ai/docs/guides/features/structured-outputs

Для другого OpenAI-compatible API задайте base/model/key. Если JSON Schema не поддерживается, явно установите `AI_STRUCTURED_OUTPUT=json_object`; автоматического downgrade нет. Сравнение разных провайдеров выполняйте с одинаковым gold и промптом, учитывая возможные различия в поддержке схемы.

## Проверка качества на DEV

`invoke.json` и набор, полученный по ссылке из PDF, проверены: все 65 записей полностью совпадают (35 RU, 15 KZ, 15 EN; 60 чатов, 5 звонков). Исходные переписки и подписанная ссылка в Git не добавлены.

Предварительные 72 оценки на девяти реальных диалогах находятся в [`tests/fixtures/ai-gold.draft.json`](../tests/fixtures/ai-gold.draft.json). Есть идентификация, N/A, обрыв, частная платная услуга, раскрытие сведений без проверки и звонок с ASR. Нюансы и матрица — [`ai-gold-review.md`](ai-gold-review.md). **Это подготовленная агентом разметка, а не ручное согласование с командой и не ответы облачной модели.**

Порядок:
1. Команда независимо проверяет все 72 ответа, причины и доказательства; особенно спорные `c7` и ASR. При необходимости правит JSON.
2. Сохраняет согласованный gold с `status: "approved"`, непустым `approved_by` и snapshot реальных критериев. Не утверждайте файл механически только для запуска команды.
3. Выполняет обе модели на одном наборе. Если рубрика изменилась, benchmark откажется до повторной разметки — старый gold нельзя применять к новой версии.

```sh
npm run ai:benchmark -- \
  --version UUID_ВЫБРАННОЙ_ВЕРСИИ \
  --dataset "/home/angel/Загрузки/Telegram Desktop/invoke.json" \
  --gold tests/fixtures/ai-gold.draft.json \
  --models stealth/crouton-alpha,openai/gpt-4.1-mini
```

Без утверждённого gold команда откажется. Для **явно предварительного** исследования есть `--allow-draft`; такой отчёт всегда имеет `preliminary=true`. Не используйте его как согласованную точность.

Результат: `data/ai-results/benchmark.json`. Сравнение — точное совпадение пары `answer + raw_score`, максимум 72 на модель; отдельно RU/KZ/EN (24 на язык), неуспешные вызовы, ошибки JSON/контракта по попыткам, количество попыток и время каждого диалога. В отчёте сохраняются реальные успешные ответы, ID и хэши входных данных, gold и исходников промпта/схемы. При изменении промпта/схемы во время прогона сравнение признаётся невалидным. Модели вызываются последовательно; никакой модели-fallback.

Отличие evidence от gold — **кандидат на ручной разбор**, а не автоматически неверное доказательство: правильных фрагментов может быть несколько. Для окончательной таблицы проверяющий должен также проверить совпавшие ссылки, текст объяснений и пропуски. Число реально неверных доказательств нельзя честно получить одним сравнением номеров. Сравните и перенос правила, создав через UI новую версию с заменённым критерием и прогнав одиночный CLI; старый benchmark к ней намеренно не подходит.

Текущий статус измерений и технических тестов — [`ai-validation.md`](ai-validation.md).
