# План проверок причин ошибок CQA-модели

Дата: 2026-11-07. Модель — текущая `stealth/crouton-alpha`; базовый исследуемый промпт — неизменённый v2. Это причинные пилотные проверки, не поиск максимального совпадения с draft и не официальный контроль. Рабочие v1/v2, база, маршруты, `score.js` и `results/dev/results.json` не изменяются. Экспериментальные условия хранятся отдельно.

## До первых API-вызовов

CLI `scripts/hypothesis-study.js --plan` сохраняет неизменяемый `data/ai-results/hypotheses/plan.json`: полный список 40 задач, точные промпты/преобразования/синтетические входы, хэши исходного DEV, версии, кода и настроек. Изменение fingerprint останавливает вызовы. Контрфактические справочные факты и ожидаемые оценки не подставляются в настоящие DEV-диалоги. Эталоны и oracle не отправляются модели как желаемые ответы.

Лимит: **40 начальных запросов** плюс максимум один repair некорректного JSON/контракта на запрос. Последовательное выполнение, пауза 4 секунды вне измерения оценки. Модель/endpoint/temperature=0/лимиты одинаковы; транспортных retries или скрытой смены модели нет. Сбои сохраняются отдельно от качества и не заполняются выдуманными ответами.

В исследовательском клиенте допускается один критерий для H3, но публичный `evaluateDialogue()` остаётся восьмикритериальным. Никаких фиктивных семи ответов для дополнения subset нет.

## H1. Двусмысленная формулировка исключений

**Предположение:** текст «Порог первой реакции 3 минуты, теги и вложения не оцениваются» может читаться как отдельное требование по времени, хотя исходный PDF исключает все три пункта.

- 4 настоящих диалога: `p1-ru-014`, `p1-kz-008`, `p1-en-013`, `p1-en-015`.
- Контроль: исходный c6. Воздействие: только указанная фраза заменяется на однозначное исключение, с сохранением числа «3», весов, типа и шкалы. Обе исследовательские копии версии имеют id/version=null, одинаковое имя; source-version записан отдельно. Нельзя менять эту настройку в рабочей базе по результатам без согласования.
- Промпт и транскрипт одинаковы. Порядок двух условий чередуется. **8 запросов**.
- Первичная метрика: число объяснений c6, действительно использующих исключённый SLA для снижения оценки; не любое упоминание времени. Дополнительно — неподтверждённые расчёты времени и изменение c6.
- Поддержка гипотезы: в контрольных ответах наблюдается нарушение, а явная формулировка уменьшает его без смены фактов. Если контроль не воспроизвёл ошибку, эффект в этом запуске не установлен. Любое изменение балла само по себе не доказательство исправления.

## H2. Свободное объяснение допускает достраивание фактов

**Предположение:** просьба объяснить решение свободным текстом провоцирует правдоподобное, но не подтверждённое исходником описание действий.

- 4 настоящих диалога: `p1-kz-003`, `p1-en-014`, `p1-kz-008`, `p4-ru-001`.
- Контроль: точный v2. Воздействие: v2 с отдельной версией `h2-proof-v1`, требующей короткого explanation: первая строка `Факт [N]: <дословный фрагмент>` и затем вывод, либо `Проверка [from-to]: действие не найдено` для отсутствия. Типы и JSON Schema те же.
- **8 запросов**, чередование порядка. Нарушение префикса — метрика вмешательства, а не повод отправлять дополнительный repair, которого нет у контроля.
- Метрики: неподтверждённые фактические утверждения по отдельному source-based аудиту; точность цитат и ролей; соблюдение требуемой структуры. Цитата с правильным номером не считается доказательством правильности вывода автоматически.
- Поддержка гипотезы: меньше неподтверждённых утверждений, не только больше формально найденных цитат. Непроверенное корпоративное правило учитывать отдельно от вымышленного действия; ASR-сомнения не объявлять доказанными ошибками.

## H3. Совместная оценка восьми критериев перегружает задачу

**Предположение:** внимание к восьми решениям за один вызов ухудшает оценку отдельных сложных критериев.

- 3 диалога: `p1-ru-001`, `p1-kz-008`, `p1-en-015`.
- Контроль: один полный вызов v2 на каждый диалог. Воздействие: три независимых вызова по c2, c6 и c7, каждый видит весь диалог, но только выбранный критерий. Unit-промпт сохраняет правила v2, меняет только версию и число результатов.
- **12 запросов**: 3 полных и 9 одно-критериальных. Валидация subset не изменяет production-контракт.
- Метрика: совпадение answer+raw_score по 9 целевым решениям с заранее существующим draft; отдельно сомнения разметки, состав JSON, суммарное время и количество запросов. Не сравнивать 24 общих ответа с 9 выбранными.
- Поддержка гипотезы: unit даёт больше совпадений по тем же целям. Даже положительный сигнал не оправдывает внедрение без учёта стоимости/времени и проверки на новых данных. Эти 9 решений не являются официальным Ground Truth.

## H4. Система недетерминирована даже при temperature=0

**Предположение:** одинаковый запрос не всегда возвращает одинаковые ответы/ступени, независимо от качества промпта.

- Те же три диалога H3. Полные контрольные ответы H3 — повтор №1. Добавляются два полностью одинаковых v2-запроса на каждый: **6 новых запросов**.
- Первый request SHA-256 обязан совпасть у трёх повторов. Никаких nonce, номера повтора или task-ID внутри тела. Провайдер и resolved model записываются.
- Метрика: сколько из 24 пар «диалог × критерий» меняют answer/raw_score между повторами. Различия формулировок объяснения считать отдельно. Основной тест одинакового тела — успешные ответы без repair, поскольку repair добавляет другое сообщение; остальные показываются отдельно.
- Поддержка: хотя бы одно различие решений при идентичном исходном теле и сопоставимом провайдере. Совпадение трёх повторов не доказывает универсальный детерминизм; изменение не определяет само по себе, какое решение правильно.

## H5. Часть «ошибок модели» — нестабильность предварительной разметки

**Предположение:** по спорным критериям независимые проверяющие сами не воспроизводят один ответ.

- До слепой повторной разметки отдельно сохранены `h5-blind-request.json` и закрытый `h5-selection-key.json`.
- Детерминированный отбор по SHA-256 с seed `tumo-hypothesis-h5-v1`: по 3 заранее отмеченных спорных и 3 остальных решения для каждого RU/KZ/EN. Всего **18 решений: 9+9**. В выборке 8 диалогов.
- Другой агент прочитал исходники полностью, не читая прежние labels, модельные ответы или промпты. Он получил только пары ID/критерий, не сведения о bucket, и дал независимые ответы/уверенность. Это выполнено отдельно до 40 API-задач; запросов к Crouton здесь **0**.
- Метрика: разногласия старой и независимой разметки по двум заранее определённым группам, с причинами и уверенностью. Более высокая доля разногласий в спорной группе поддерживает ограничение метрики accuracy; разногласия в другой группе тоже не скрываются.
- Оба проверяющих — агенты, не официальные эксперты. Ни одно новое решение автоматически не заменяет старое; независимость просмотра не превращает мнение в Ground Truth.

## H6. Без достоверной базы знаний нельзя надёжно проверить консультацию

**Предположение:** отсутствие независимых правил компании ограничивает проверку правильности, сколько бы ни уточнять формулировку промпта.

- Два явно вымышленных учебных диалога RU/EN, **не DEV и не правила Freedom Broker**.
- Оператор называет стоимость 5 условных единиц / срок 2 дня. Три условия при одинаковом диалоге: нет reference_material, справочник подтверждает (5 / 2), справочник противоречит (7 / 5).
- Во всех трёх условиях один и тот же промпт с явной ролью доверенного учебного справочника. Между ненулевыми справочниками меняется только числовой факт, не название вроде «верно/неверно» и не ожидаемый балл.
- **6 запросов**. Для предоставленных фактов заранее задан oracle c4: подтверждение → 20, противоречие → 0. Без справочника числового oracle **нет**: проверяется только честное указание границ уверенности, без самовольного N/A.
- Поддержка: модель меняет оценку правильно при противоположных фактах и явно признаёт отсутствие проверки без справочника. Это демонстрация на учебных фактах, не доказательство готовности реального RAG или правильности любой корпоративной базы.

## Границы выводов

Это малые диагностические абляции на уже известных DEV-примерах и двух учебных сценариях, а не новый независимый тест всей системы. Смешанный или отрицательный результат сохраняется. Не выбирать удачнейшую попытку, не править labels под ответы и не переносить экспериментальные правила в рабочий чек-лист автоматически. Вмешательства проверяются по одному; проверка полезной комбинации — отдельный будущий эксперимент.

Реализация: [`hypothesis-client.js`](../scripts/hypothesis-client.js), [`hypothesis-study.js`](../scripts/hypothesis-study.js). Закрытые ответы и диагностика находятся в `data/ai-results/hypotheses/`. План выполнен без изменения условий: [результаты и ограничения](hypotheses-results.md).
